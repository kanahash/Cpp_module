# C++ - Module 01 ex00: 要点まとめ（Memory Allocation）

このモジュールの核心は、C++における **Stack（スタック）** と **Heap（ヒープ）** の使い分け、および **`new/delete`** の作法を習得することにあります。

---

## 1. Stack（スタック）と Heap（ヒープ）の決定的な違い

### ■ Stack（スタック）割り当て：`randomChump`

| 項目 | 詳細 |
| :--- | :--- |
| **宣言方法** | 関数の中で `Zombie zombie(name);` と宣言 |
| **寿命** | その関数（スコープ）が終了すると、**自動的にデストラクタが呼ばれて消滅**。 |
| **利点** | **高速**。メモリ解放を意識する必要がなく、リークの心配がない。 |
| **欠点** | 関数外にオブジェクトを持ち出せない。メモリ容量が小さい（スタックオーバーフローのリスク）。 |
| **用途** | **「その関数の中だけで使い切る」** 一時的な利用に最適。 |

### ■ Heap（ヒープ）割り当て：`newZombie`

| 項目 | 詳細 |
| :--- | :--- |
| **宣言方法** | `new` キーワードを使い、`Zombie* zombie = new Zombie(name);` と宣言 |
| **寿命** | **`delete` を呼ぶまで** 生き続ける。 |
| **利点** | ポインタを `return` して他の場所で使い続けられる。システム全体の空きメモリを利用でき、巨大なデータも扱える。 |
| **欠点** | **手動で `delete` しないとメモリリークになる**。 |
| **用途** | **「オブジェクトを関数の外に持ち出したい」**、**「生存期間を自由にコントロールしたい」** 場合に使用。 |

---

## 2. `new` キーワードの使い方

ヒープ領域にメモリを確保し、オブジェクトの **コンストラクタを呼び出す** ための演算子です。

### ① 基本構文

| パターン | 構文（生成） | 構文（解放） |
| :--- | :--- | :--- |
| **単一オブジェクト** | `Zombie* z = new Zombie("Foo");` | `delete z;` |
| **配列の生成** | `Zombie* horde = new Zombie[10];` | `delete[] horde;` |

* メンバ関数へのアクセスには `->` アロー演算子を使用します。

### ② `new` が裏側で行っていること

以下の3工程を自動で行います。

1.  **メモリの確保**: ヒープから必要なバイト数を探す。
2.  **コンストラクタの呼び出し**: 確保した領域でコンストラクタを実行し、初期化する。
3.  **アドレスの返却**: 正しい型のポインタとしてアドレスを返す。

---

## 3. `delete` と `delete[]` の厳格な使い分け

| 確保の方法 | 解放の方法 | 理由 |
| :--- | :--- | :--- |
| `new Zombie()` | `delete z;` | 1つのインスタンスのデストラクタを呼ぶため |
| `new Zombie[N]` | `delete[] z;` | **全要素（N個分）** のデストラクタを順番に呼ぶため |

---

## 4. 注意点：メモリリークの発生条件

* `delete` を呼ぶ前に、ポインタ変数に別の値を代入したとき。
* `delete` を呼ぶ前に、ポインタ変数がスコープを抜けたとき。

> **Key Rule**: 「その関数の中で使い切るなら Stack。外に持ち出すなら Heap」

---

## 5. 課題のポイント

### ➀ メモリ割り当ての選択

| 関数 | 割り当て | 理由/目的 |
| :--- | :--- | :--- |
| `randomChump` | **Stack** | その場限りの利用。最も安全で高速なスタック割り当てを選択。 |
| `newZombie` | **Heap** | 関数の外にオブジェクトを持ち出し、後で利用・破棄できるようにするため、ポインタを返すヒープ割り当てを選択。 |

### ➁ デストラクタの役割の明確化

デストラクタ内で、ゾンビの名前を含むログ（例：`<name>: died`）を必ず出力する。

* **randomChump**: 関数実行後に**自動的に**ログが出ることを確認。
* **newZombie**: `delete` を実行した瞬間に**手動で**ログが出ることを確認。

### ➂ `newZombie` での責任の所在

* **原則**: `newZombie` 関数は `new` を実行するだけで、`delete` を実行してはいけない。
* **理由**: `newZombie` はオブジェクトを生成し、その制御権を呼び出し元に渡す役割のため。
* **責任**: `new` をした側のポインタを追跡し、責任を持って `delete` を実行するのは、ポインタを受け取った側の役割。

---

## 6. 必須の検討事項（メモリ安全性の証明）

### ➀ ライフタイムの正確な証明（ログによる検証）

* **randomChumpの検証**: `randomChump()` の呼び出しが終了した直後に、ゾンビのデストラクタログが出ていること。
* **newZombieの検証**: `delete` のタイミングでデストラクタログが出ていること。

### ➁ メモリリークの徹底的な排除

* **valgrindの使用**: 実行ファイルに対して `valgrind ./<executable>` を実行し、**「0 bytes in 0 blocks」**の状態を確認する。
* **検出**: `newZombie` で作成したゾンビを `delete` し忘れた場合、メモリリークとして即座に検出される。

### ➂ エラー処理の確認（応用）

* **無効なポインタ**: `new` で返されたポインタに対して、`delete` を実行する前に再度 `new` で上書きした場合、**もとのメモリがリークする**ことを確認する。
