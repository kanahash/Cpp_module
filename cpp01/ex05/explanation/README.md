## 🛠️ C++ Module 01 ex05: 要点まとめ（Harl 2.0）

### 1. 課題の目的
* **「Harl」クラスの作成**: 
    Harlには4つのレベル（DEBUG、INFO、WARNING、ERROR）があり、入力されたレベルに応じて適切なプライベート関数を呼び出す必要がある。
* **最大の制約**: 
    `if / else if / else` を使わずに、関数の呼び出しを実装する必要がある。

### 2. 関数ポインタの配列（メンバ関数ポインタ）
通常の関数ポインタとは異なり、クラスのメンバ関数を指すポインタの作法を学ぶ。

#### ○ メンバ関数ポインタの宣言と定義
クラスHarlのメンバ関数を指すポインタの型は以下の通り。
* `void (Harl::*fPtr)(void);`
これを配列にすることで、インデックスやループを使って関数を選択できるようになる。



#### ➀ メンバ関数ポインタの具体的なシンタックス
通常の関数ポインタと違い、どのクラスに属する関数かを示す `Harl::` が必要である。
* **定義例**: `void (Harl::*fPtr)(void);`
* **構文**: `戻り値の型 (クラス名::*ポインタ変数名)(引数の型);`

#### ➁ アドレスの代入
メンバ関数のアドレスを取得する際は、必ず **`&` 演算子** と **完全修飾名** を使用する。
* **例**: `fPtr = &Harl::debug;`

#### ③ ポインタ配列の初期化
ex05の実装で推奨される、名前（文字列）と関数を一対一で結びつける方法。
※詳細は実装のセクションにて。

#### ④ 関数の呼び出し
ポインタ経由で実行する際は、`this` ポインタと `.*` または `->*` 演算子を使用する。**演算子の優先順位の関係でカッコが必須**である。
* **呼び出し例**: `(this->*functions[i])();`
* **構文**: `(インスタンスのポインタ->*ポインタ変数名)();`

### 3. 実装のアルゴリズム
`complain(std::string level)` 関数の中では、以下のフローで処理を行う。

* **➀ レベル名の配列を用意する**: (例：`{"DEBUG", "INFO", "WARNING", "ERROR"}`)
* **➁ メンバ関数ポインタの配列を用意する**: 各レベルに対応するプライベート関数（`debug()`, `info()` など）のアドレスを格納する。
* **③ ループで検索**: 入力された `level` が、レベル名配列の何番目にあるか探す。
* **④ 関数の実行**: 見つかったインデックスを使って、関数ポインタ配列から関数を呼び出す。



#### ○ 呼び出しの構文
メンバ関数ポインタを介して関数を呼ぶ際は、`this` ポインタを使用する。
* **例**: `(this->*fPtr[i])();`

---

### 4. なぜこの設計が必要なのか（保守性）
* **可読性**: 
    20個、30個と条件が増えた場合、`if-else` は非常に読みづらくなるが、配列によるマッピング（ジャンプテーブル）ならコードの長さは変わらない。
* **拡張性**: 
    新しいレベルを追加したい場合、配列に要素を追加するだけで済み、`complain` 関数のロジック本体を修正する必要がない。
* **効率**: 
    ループやテーブルによる検索は、複雑な条件分岐よりも意図が明確でミスが減る。



---

### 5. 注意点
* **プライベート関数**: 
    `debug()`, `info()` などの具体的な内容は `private` メンバにする必要がある。外部からは `complain()` という入り口が一つだけ見えるようにする（カプセル化）。
* **エラーハンドリング**: 
    定義されていないレベル名が入力された場合、クラッシュせずに何もしない、あるいは適切なメッセージを出して終了するようにする。

---

### 6. 必須のテスト項目
Harlが正しく、かつ堅牢に動作するかを確認するために以下のテストを行う。

#### ➀ 全ての有効なレベル
* **DEBUG**: 「デバッグ情報」が出るか
* **INFO**: 「補足情報」が出るか
* **WARNING**: 「警告」が出るか
* **ERROR**: 「致命的なエラー」が出るか

#### ➁ 無効なレベル（不正な入力）
* **空文字**: `complain("")` を呼び出した時、プログラムがクラッシュせずに無視されるか。
* **存在しないレベル**: `complain("HELLO")` や `complain("123")` など、配列にない文字列を渡した際に適切に処理されるか。
* **大文字小文字の区別**: `complain("debug")`（小文字）を渡した際、"DEBUG"と一致せずに何も起きない（またはエラーログが出る）か。

#### ③ 連続呼び出し
* 同じレベルを連続で呼んだり、異なる順序で呼んだりして、データや状態が壊れないか確認。

---

### 7. レビューで聞かれるかもしれないポイント
* **➀ 「なぜ if-else を使ってはいけないのか」**
    → 保守性を高めるため。条件が増えた際に関数ポインタの配列（テーブル）に一行追加するだけで済み、ロジック本体を修正せずに拡張できる（Open-Closed Principle）。
* **➁ 「this->*functions[i]() のカッコを外すとどうなるか」**
    → 演算子の優先順位により、関数呼び出し `()` が先に評価されてしまい、コンパイルエラーになる。ポインタの参照を先に行うためにカッコが必須。



---

### 8. まとめ

| 項目 | 内容 |
| :--- | :--- |
| **技術的要素** | メンバ関数ポインタ、ポインタの配列 |
| **禁止事項** | 大量の `if/else if/else` による分岐 |
| **設計思想** | データと処理の分離、拡張性の確保 |
| **呼び出し方** | `(instance.*ptr)()` または `(this->*ptr)()` |

---

### 2. ③ 実装のコード例
```cpp
void Harl::complain(std::string level) {
    // レベル名の配列
    std::string levels[] = { "DEBUG", "INFO", "WARNING", "ERROR" };

    // メンバ関数ポインタの配列
    void (Harl::*functions[])(void) = {
        &Harl::debug,
        &Harl::info,
        &Harl::warning,
        &Harl::error
    };

    for (int i = 0; i < 4; i++) {
        if (levels[i] == level) {
            (this->*functions[i])();
            return;
        }
    }
}
